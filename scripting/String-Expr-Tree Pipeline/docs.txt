======================================================================
IMPLEMENTATION STATUS (as of current version)
======================================================================

All stages described here are implemented.  The public entry point is:

    from pipeline import raw_latex_to_tree
    tree = raw_latex_to_tree(raw_latex_string)

See pipeline.py for full API docs.

======================================================================
A. FULL PIPELINE OVERVIEW
======================================================================

Effective pipeline (raw LaTeX -> ExpressionTree):

  Stage 1   raw LaTeX string
            -> strip equation/environment wrappers (\begin{...}, \[...\], $$)
  Stage 2   -> remove equation metadata (\label, \tag, \nonumber, \notag, ...)
  Stage 3   -> split multiline equations into separate candidates (on \\)
  Stage 4   -> extract RHS of each equation (split on bare =, depth-aware)
              [if no = found: use the whole line as the candidate]
  Stage 5   -> reject or unwrap banned constructs (integrals, sums, ...)
  Stage 6   -> normalize LaTeX (strip decorators, \left/\right, spacing, ...)
  Stage 6.5 -> strip ambiguous Greek whole-wrappers (see Section D)
  Stage 7   -> reject unknown LaTeX commands (whitelist in _KNOWN_COMMANDS)
  Stage 8   -> parse normalized LaTeX with SymPy parse_latex
  Stage 9   -> replace Derivative(...) subexpressions with placeholder symbols
  Stage 10  -> filter scalar/constant terms (see Section E)
  Stage 11  -> convert SymPy expr to ExpressionTree (sympy_to_tree_2.py)
  -> reject trivial bare-symbol / bare-number results
  -> save cleaned_latex + sympy_str = str(sympy_expr)
  -> later convert SymPy expr to project ExpressionTree using sympy_to_tree_2.py

Important note:
- latex_cleaner.py DOES use SymPy parse_latex.
- It then saves the parsed expression as a string using str(expr).
- It does NOT call sympy_to_tree_2.py directly.
- A later bridge step is still needed to go from saved sympy_str back to a SymPy expression object,
  unless the SymPy object is kept in memory.

======================================================================
B. ADDITIONAL RULES CURRENTLY IMPLEMENTED IN latex_cleaner.py
======================================================================

B1. Strip outer wrappers before parsing
--------------------------------------
Raw equations are not parsed as-is.
The cleaner first removes outer wrappers such as:
- \begin{...} ... \end{...}
- \[ ... \]
- $$ ... $$

Reason:
- Raw paper equations often appear inside display environments that should not be sent directly to SymPy.


B2. Remove equation metadata commands
-------------------------------------
The cleaner removes metadata-like commands before parsing, including:
- \label{...}
- \tag{...}
- \nonumber
- \notag
- \eqnr
- \eqnumber

Reason:
- These are not mathematical content and interfere with direct parsing.


B3. Split multiline equations into separate line candidates
-----------------------------------------------------------
The cleaner splits on LaTeX line breaks (\\), excluding spacing forms like \\[...].
Each resulting line is processed independently.

Reason:
- align / align* / eqnarray style environments often contain multiple equations.


B4. Extract only the RHS of equations
-------------------------------------
Each line is stripped of alignment markers (&), then split on bare '=' signs at brace depth 0.
The cleaner keeps only the final RHS segment.

Examples:
- x = y + z            -> y + z
- a = b = c + d        -> c + d

Reason:
- The downstream tree pipeline is expression-oriented, not full-equation-oriented.

Consequence:
- The left-hand side is discarded.
- Equation identity / defined variable information is lost.


B5. Reject banned constructs before SymPy parsing
-------------------------------------------------
If a candidate contains banned constructs, it is rejected before parse_latex,
unless the banned construct is the sole outer wrapper around the entire candidate.

Currently banned construct families include:
- Integrals: \int, \oint, \iint, \iiint, etc.
- Gradient/vector ops: \nabla
- Large operators: \sum, \prod, \coprod, \bigcup, \bigcap, \bigvee, \bigwedge
- Limits / extrema / arg ops: \lim, \limsup, \liminf, \inf, \sup, \arg, \argmin, \argmax, \min, \max
- Dot / cross / tensor / logic-style ops: \cdot, \times, \otimes, \oplus, \wedge, \vee
- Nested environment markers: \begin, \end
- Text/layout commands: \text, \mbox, \textrm, \textit, \textbf, \textsc, \intertext,
  \hline, \cline, \multicolumn, \multirow
- Quantifiers: \forall, \exists
- Ellipsis commands: \cdots, \ldots, \vdots, \ddots
- Overset/underset wrappers: \overset, \underset, \stackrel, \overbrace, \underbrace
- Custom operator wrapper: \operatorname
- Modulo forms: \pmod, \bmod
- Norm delimiter command: \|

Reason:
- These either carry unsupported semantics, introduce non-scalar structure, or are outside the tree vocabulary.


B6. Sole-wrapper unwrapping rule for banned constructs
------------------------------------------------------
If a banned construct is the ONLY outer wrapper around the full candidate, the cleaner strips the wrapper
and recursively cleans only the inside/body.

Examples:
- \sum_{i=1}^{n}(a+b)   -> keep (a+b)
- \nabla^2 \phi         -> keep \phi
- f + \sum(g)            -> reject (because banned construct is not the whole candidate)
- \sum(a+b) + \nabla(c) -> reject (multiple banned constructs)

Important semantic consequence:
- The wrapper meaning is discarded.
- The saved expression is the inside only, not a function-like retained form.
- Example: a sole-wrapper sum becomes a+b, not sum(a+b).


B7. Safe normalization before parsing
-------------------------------------
The cleaner applies normalization to make the expression more SymPy-friendly.
This includes:

1. Strip decorator wrappers but keep their content
   Examples:
   - \mathbf{x}   -> x
   - \hat{x}      -> x
   - \tilde{y}    -> y
   - \mathcal{F}  -> F
   - nested decorators are stripped in repeated passes

2. Remove spacing commands
   Examples:
   - \, \; \: \! -> spaces
   - \quad, \qquad -> spaces
   - \hspace{...}, \vspace{...} -> removed

3. Remove display-style annotations
   Examples:
   - \displaystyle
   - \textstyle
   - \scriptstyle
   - \scriptscriptstyle

4. Replace delimiter commands with plain delimiters
   Examples:
   - \left( ... \right) -> ( ... )
   - \left[ ... \right] -> ( ... )
   - \left| ... \right| -> | ... |
   - \langle ... \rangle -> ( ... )
   - \left. or \right. -> removed

5. Strip size modifiers
   Examples:
   - \big, \Big, \bigl, \bigr, etc. -> removed

6. Remove trailing punctuation from equation text
   Examples:
   - trailing '.', ',' or ';' appended in prose after equations

7. Collapse repeated whitespace

Reason:
- Many TeX formatting commands should not affect symbolic meaning and would otherwise block parsing.


B8. Reject unknown LaTeX commands using a whitelist
---------------------------------------------------
Before parsing, the cleaner scans all \command tokens.
If any command is not in the known-command whitelist, the candidate is rejected.

Whitelisted categories include:
- Allowed trig/hyperbolic/log commands:
  sin cos tan cot sec csc arcsin arccos arctan arccot sinh cosh tanh coth exp log ln
- Other allowed functions:
  sqrt abs
- Fraction commands:
  frac dfrac tfrac
- Greek letters (lower- and uppercase)
- partial
- Common symbols like infty, pm, mp, prime, ell
- Some relation tokens like approx, equiv, propto, leq, geq, neq, ll, gg, not
- Delimiter names and misc tokens like limits, nolimits

Reason:
- Custom macros and unknown commands are too ambiguous for direct parsing.

Consequence:
- A custom macro such as \foo or \relu is rejected, even if it looks function-like.


B9. Derivatives are allowed through parse_latex, then replaced with symbols
---------------------------------------------------------------------------
Contrary to a simplistic "ban derivatives" policy, the current implementation does NOT ban \partial.
Instead:
- partial is allowed in the command whitelist
- derivative syntax is allowed to reach parse_latex
- after SymPy parsing, any Derivative(...) subexpression is replaced with a fresh Symbol
  such as _dv0, _dv1, etc.

Example behavior:
- x + Derivative(f(x), x) -> x + _dv0

Reason:
- Preserve the surrounding scalar expression even when derivative structure is unsupported downstream.

Consequence:
- Derivative meaning is lost and replaced by placeholder variable semantics.


B10. Reject trivial parse results
---------------------------------
Even if SymPy parsing succeeds, expressions that reduce to a bare Symbol or bare Number are rejected.

Examples:
- x   -> reject as trivial_expr
- 3   -> reject as trivial_expr

Reason:
- These are usually too degenerate to be useful for tree-learning.


B11. Save SymPy output as a string, not as a tree
-------------------------------------------------
Successful parse outputs are stored as:
- cleaned_latex
- sympy_str = str(sympy_expr)

Reason:
- latex_cleaner.py only performs the cleaning + parse stage.
- Tree conversion is deferred.

======================================================================
C. ADDITIONAL RULES CURRENTLY IMPLEMENTED IN sympy_to_tree_2.py
======================================================================

These rules apply AFTER a valid SymPy expression object exists.
They are not part of raw-LaTeX cleaning, but they are part of the full pipeline behavior.

C1. Convert SymPy expressions to project Node / ExpressionTree form
-------------------------------------------------------------------
The converter maps a subset of SymPy syntax into the project's operator vocabulary.
Anything outside this supported subset raises UnsupportedExprError.


C2. Supported leaf handling
---------------------------
- Symbols become symbolic leaf nodes.
- Numbers become symbolic leaf nodes containing their string form.
- Constants are canonicalized as:
  - pi -> "pi"
  - E  -> "e"
  - I  -> "i"


C3. Add handling
----------------
SymPy Add expressions become project add nodes with children for each argument.
Subtraction is not preserved as a separate operator; it is represented through Add and negation.

Example idea:
- a - b  -> add(a, neg(b))


C4. Mul handling with sign extraction and denominator extraction
----------------------------------------------------------------
SymPy Mul expressions are canonicalized with these rules:
- negative signs are pulled out into an explicit unary neg node
- negative integer powers are moved into the denominator

Examples:
- -x              -> neg(x)
- x * y**-1       -> div(x, y)
- x * y**-2       -> div(x, pow2(y))
- -2*x            -> neg(mul(2, x))
- a*b*c           -> mul(a, b, c)


C5. Power handling and canonical special cases
----------------------------------------------
Pow(base, exp) is converted using special rules:
- x**(1/2)  -> sqrt(x)
- x**-1     -> div(1, x)
- x**2      -> pow2(x)
- x**3      -> pow3(x)
- x**4      -> pow4(x)
- x**-2     -> div(1, pow2(x))
- x**-3     -> div(1, pow3(x))
- x**-4     -> div(1, pow4(x))
- other integer or general powers -> pow(base, exp)


C6. Supported unary function map is limited
-------------------------------------------
Only the following SymPy unary functions are explicitly supported:
- sin
- cos
- tan
- exp
- log
- Abs
- asin
- acos
- atan
- sinh
- cosh
- tanh

These are mapped to project op names like:
- asin -> arcsin
- acos -> arccos
- atan -> arctan
- Abs  -> abs

Consequence:
- If the cleaner allows something like sigma(...), and it remains as a SymPy function call,
  sympy_to_tree_2.py will reject it unless support is added.


C7. Unsupported SymPy structures raise errors
---------------------------------------------
Examples likely to fail unless specially handled:
- unknown applied functions such as sigma(...)
- Piecewise
- matrices / tensors
- relational expressions
- unsupported special functions
- non-finite values such as NaN or Infinity


C8. Final tree is wrapped in a root id node
-------------------------------------------
The converted expression is wrapped in a ROOT(id) node for consistency with project tree conventions.

======================================================================
D. AMBIGUOUS GREEK WHOLE-WRAPPER STRIPPING (Stage 6.5) — IMPLEMENTED
======================================================================

Implemented in latex_cleaner.py: strip_greek_wrapper() and _AMBIGUOUS_GREEK.
Applied in clean_to_expr() in a loop after Stage 6 (normalise), before Stage 7
(unknown commands).  Stripping is applied until no further outer wrappers remain.

D1. Ambiguous Greek-letter commands followed immediately by '(' should be treated as function-like wrappers
-------------------------------------------------------------------------------------------------------------
Proposed rule:
If an ambiguous allowed Greek-letter command is immediately followed by an open parenthesis,
treat it as a wrapper/function-like construct rather than as a plain variable.

Examples of ambiguous allowed commands:
- \sigma
- \mu
- \nu
- and potentially similar allowed Greek-letter names like phi, rho, psi, etc.

Motivation:
- In raw LaTeX, commands like \sigma are Greek letters, not standard built-in math functions.
- But in some papers they are used as function names, especially in ML (e.g. sigmoid).
- If sent directly to SymPy, they may parse as unknown applied functions and later break tree conversion.


D2. When such an ambiguous Greek-letter wrapper is the whole candidate, strip the wrapper and keep only the inside
------------------------------------------------------------------------------------------------------------------
Proposed behavior:
- \sigma(x+y)   -> keep x+y
- \mu(a/b)      -> keep a/b
- \nu(z^2)      -> keep z^2

This matches the existing sole-wrapper logic for banned constructs.

Important semantic consequence:
- The wrapper meaning is discarded.
- Example: if \sigma means sigmoid, the resulting cleaned expression keeps only the argument,
  not the sigmoid operation.


D3. Apply the ambiguous-Greek-wrapper rule AFTER normalization
-------------------------------------------------------------
Recommended placement:
- run substitute_latex first, so forms like \sigma\left(x\right) become \sigma (x) or \sigma(x)
- then detect the pattern more easily

Reason:
- This avoids needing to separately match raw \left( and normalized '(' forms.


D4. Restrict the ambiguous-Greek-wrapper rule to whole-candidate wrappers only
-----------------------------------------------------------------------------
Recommended safety condition:
Only strip the wrapper when the entire cleaned RHS has the form:
- \sigma(...)
- \mu(...)
- \nu(...)
- etc.

Do NOT silently strip internal occurrences inside larger expressions.

Examples:
- \sigma(x)            -> okay to strip to x
- a + \sigma(x)        -> do NOT silently rewrite to a + x
- \sigma(x) + \mu(y)  -> do NOT apply this simplistic whole-wrapper rule independently unless a more careful policy is added

Reason:
- Stripping internal wrappers inside larger expressions changes structure too aggressively.


D5. Distinguish variable-vs-function use of ambiguous Greek commands heuristically by syntax
---------------------------------------------------------------------------------------------
Heuristic agreed in chat:
- If an ambiguous Greek command is followed by parentheses, treat it as function-like.
- If it appears in ordinary algebraic symbol position, treat it as a variable/symbol.

Examples likely treated as variable/symbol:
- \sigma + x
- 2\sigma
- \sigma_i
- \sigma^2

Examples likely treated as function-like wrapper:
- \sigma(x)
- \sigma\left(x+y\right)

Important note:
- This is only a heuristic; LaTeX itself does not reliably encode semantic intent here.


D6. The goal of these extra rules is conservative tree-safe salvage, not full semantic preservation
---------------------------------------------------------------------------------------------------
The agreed direction in chat favors:
- keeping a parseable scalar inner expression
- avoiding unsupported function nodes leaking into sympy_to_tree_2.py
- accepting semantic loss when necessary

That means the pipeline is intentionally closer to:
- "salvage the inner scalar algebra"
than to:
- "faithfully preserve every operator/function from the paper"

======================================================================
E. SCALAR / CONSTANT FILTERING (Stage 10) — IMPLEMENTED
======================================================================

Implemented in scalar_filter.py: filter_scalars().
Applied in pipeline.py after Stage 9 (parse + derivative replacement).

Scalar definition:
  An expression is "scalar" if expr.free_symbols == set().
  This includes: integers, rationals, floats, pi, E, I, and their
  combinations.  Raw Symbol objects are NEVER scalar by this definition.

Filtering rules (top-level only — not inside function arguments):
  1. Add: remove terms with no free symbols.
  2. Mul: remove factors with no free symbols (including the sign -1).
  Applied sequentially: Add first, then Mul on the result.

Sign policy:
  Negation is Mul(-1, x) in SymPy; -1 is scalar and is dropped.
  So -x → x, -sin(x) → sin(x).
  This is intentional: linear transformations (a·f + b) are external.

Examples:
  x + 3             → x
  2 * x             → x
  (3/7)*sin(x) + 4  → sin(x)
  -sin(x)           → sin(x)
  x * y             → x * y    (no scalars at top level)
  sin(x + 3)        → sin(x + 3)  (3 is inside a function arg, untouched)

Fallback:
  If filtering would remove everything, the original expression is
  returned unchanged (no error is raised).

Limitation:
  Raw symbol names (e.g. "c") are NOT treated as scalar even if they
  conceptually represent a constant in the paper.  Only numeric/constant
  SymPy atoms are filtered.

======================================================================
F. PRACTICAL SUMMARY: WHY RAW LATEX -> SYMPY ALONE IS NOT ENOUGH
======================================================================

A naive raw-LaTeX -> SymPy approach fails because paper equations often contain:
- display/environment wrappers
- metadata tags
- multiline alignment syntax
- equation LHS + RHS structure
- unsupported large operators and vector operators
- decorator/font commands
- spacing/display formatting commands
- custom macros / unknown commands
- derivatives and other unsupported structures
- ambiguous symbols used as function names
- expressions that parse but are uselessly trivial

So the additional rules above are needed to:
- normalize the syntax,
- reject unsupported structures,
- unwrap some wrappers conservatively,
- preserve usable scalar subexpressions,
- and match the downstream tree vocabulary.

======================================================================
G. IMPLEMENTATION ORDER NOTE (for reference)
======================================================================

Actual processing order within clean_to_expr() (Stages 5-9+6.5):

1. Stage 5: banned-construct check + sole-wrapper unwrapping
2. Stage 6: substitute_latex normalisation (strips decorators, \left/\right, etc.)
3. Stage 6.5: strip_greek_wrapper loop (whole-candidate ambiguous Greek wrapper)
4. Stage 7: unknown-command whitelist check
5. Stage 8: parse_latex
6. Stage 9: replace Derivative atoms with placeholder symbols

Then in pipeline.py:

7. Stage 10: filter_scalars (scalar/constant filtering)
8. Stage 11: sympy_to_tree (SymPy → ExpressionTree)
